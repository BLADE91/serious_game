# 严肃游戏美术需求文档

## 1. 文档定位

本文档定义严肃游戏第一版及后续扩展所需的全部美术设计需求。它面向美术设计、UI 设计、前端开发、后端剧本包生成和测试验收共同使用。

美术设计不只负责“好看”，还必须服务于以下目标：

- 呈现基层治理、生态搬迁、社会动员和暗线调查的现实感。
- 帮助玩家快速判断 NPC 状态、事件风险、资源压力和剧情线索。
- 支持剧本持续更新时新增 NPC、事件、地点、结局，而不破坏程序结构。
- 让技术代码可以通过 `assets_manifest.json`、`asset_id` 和状态字段直接加载对应资源。

本文档与 `technical_design.md` 的关系：

- 本文档定义“需要画什么、交付什么规格、如何验收”。
- `technical_design.md` 定义“代码如何读取、校验、缓存和渲染这些资源”。
- 所有正式进入游戏的美术资源都必须登记到剧本包的 `assets_manifest.json`。
- `最终剧本.md` 是人物、剧情、事件日期和结局的内容权威；`art_need_arguments.md` 是已按该剧本整理的具体生产清单与提示词权威，包含 30 名独立人物、5 类事件群像、24 个场景、12 张关键事件插图和 24 张主结局封面。

## 2. 总体美术目标

### 2.1 题材表达

游戏题材是县域基层治理、生态搬迁动员、政策执行和复杂社会关系博弈。整体视觉必须克制、真实、有压力感，避免娱乐化过强。

关键词：

- 县域治理
- 生态搬迁
- 档案与会议
- 村庄社会网络
- 政策执行压力
- 舆情和信访风险
- 暗线调查
- 多主体谈判

### 2.2 风格方向

总体风格必须以 `background/美术设计/设计参考/` 中的参考图为基准。当前参考图呈现的是“政务档案式严肃游戏界面”：深色外框、旧纸张面板、手绘流域地图、半写实水彩人物肖像、档案盒、红章批注、会议材料和基层办公室环境共同构成统一视觉。

推荐风格：

- 半写实手绘 / 半纪实水彩插画。
- 政务档案、工作台、会议材料、县域治理项目资料的界面气质。
- 深色木质或黑灰色顶栏与边框，搭配旧纸张、文件夹、档案袋、红章、批注、夹子等细节。
- 人物采用半写实肖像，不是照片，也不是夸张卡通。
- 场景采用低饱和手绘写实，重点表现村庄、河流、山地、办公室、会议室、档案室。
- 地图采用手绘地形图和标绘图结合，能承载村组、河流、工厂、安置区、政府机关、NPC 房屋等信息。
- 色彩以暗黑灰、旧纸米黄、褪色墨绿、土黄、低饱和蓝灰为主，红色只用于风险、批注、警示和盖章。
- 字体气质可参考政务文件、手写标题和档案标签，但正文必须保证清晰可读。

不推荐风格：

- 夸张二次元。
- 科幻、赛博、魔幻。
- 过度卡通。
- 大面积高饱和霓虹色。
- 真实人物照片直接改图。
- 影射真实地名、真实组织或真实人物的图像。
- 现代 SaaS 纯白极简风。
- 商业手游式高光按钮、强发光边框、抽卡卡面和夸张特效。
- 过度恐怖、犯罪悬疑或废土化表达。

### 2.2.1 参考图落地规则

参考图中的可继承元素：

- 深色顶栏和功能图标区。
- 旧纸张主面板。
- 文件夹、档案袋、档案盒、红章、夹子、手写批注。
- 手绘流域地图和村庄地形。
- 左侧指标栏、中央对话/档案区、右侧地图/事件区的三栏组织方式。
- 半写实 NPC 肖像，带有年龄、职业、地域生活痕迹。
- 日终、复盘和结局页中的报告式排版。

需要控制的部分：

- 参考图里的纹理可以保留，但不能影响正文阅读。
- 纸张做旧不能过脏，避免 UI 信息失焦。
- 顶栏和边框可以厚重，但不能压缩主要内容区。
- 书法标题可用于游戏名和大标题，正文不能使用难读书法字体。
- 人物不能过度戏剧化，必须像真实基层治理场景中的人。

### 2.3 情绪基调

美术要体现“任务压力”和“现实复杂性”，但不能把界面做成恐怖、悬疑或犯罪游戏。

主要情绪：

- 日常基层工作中的繁忙感。
- 谈判现场的紧绷感。
- 村庄关系网络的复杂感。
- 暗线线索逐步浮现的疑虑感。
- 结局复盘时的制度性反思感。

## 4. 交付目录规范

正式资源建议进入每个剧本包目录：

```text
outputs/script_packages/
  pkg_YYYYMMDD_HHMMSS/
    assets_manifest.json
    art_story_mapping.json
    art/
      brand/
      ui/
      icons/
      player/
      npc/
      map/
      scenes/
      events/
      evidence/
      endings/
      tutorial/
      system/
```

开发期源文件建议单独保存：

```text
art_source/
  style_guide/
  figma_exports/
  psd_or_ai_source/
  npc/
  map/
  scenes/
  events/
  endings/
  licenses/
```

原则：

- 游戏运行时只读取 `outputs/script_packages/<package_id>/art/` 下的导出资源。
- PSD、AI、Figma 源文件不进入运行时资源目录。
- 资源源文件和导出文件必须能通过 `asset_id` 对应。
- 同一资源更新后必须提升 `version`，不能覆盖旧包中已被存档引用的资源。

## 5. 命名规则

所有资源使用稳定 `asset_id`，禁止使用中文名作为程序主键。

### 5.1 通用命名

```text
{category}_{scope}_{name}_{variant}
```

示例：

```text
brand_title_main
ui_panel_dialogue_default
icon_action_home_visit
npc_zhou_dashan_portrait_neutral
map_yunxi_liulin_overview_base
map_house_npc_zhou_dashan_default
scene_village_committee_day
event_d31_municipal_inspection_arrival
evidence_env_report_redacted
ending_main_22_cover
system_loading_llm
```

### 5.2 文件命名

文件名应与 `asset_id` 保持一致：

```text
npc_zhou_dashan_portrait_neutral.webp
event_d31_municipal_inspection_arrival.webp
icon_status_signed.svg
map_yunxi_liulin_overview_layers.svg
```

### 5.3 版本命名

`asset_id` 表示语义身份，`version` 表示版本：

```json
{
  "asset_id": "npc_zhou_dashan_portrait_neutral",
  "version": "1.0.0"
}
```

禁止用文件名追加 `final_final_2` 之类不可追踪名称。需要修改时更新 `version` 和 `updated_at`。

## 6. assets_manifest.json 规范

每个剧本包必须包含 `assets_manifest.json`。前端和后端都通过该文件读取资源，不允许在代码中硬编码具体图片路径。

```json
  "design_tokens": {
    "file": "art/ui/design_tokens.json"
  },
  "assets": []
}
```

## 7. UI 设计需求

### 7.1 页面清单

第一版必须完成以下页面设计：

| 页面 | 说明 | 美术交付 |
|---|---|---|
| 登录页 | 用户名、密码、登录按钮 | 背景、标题、表单样式、错误提示 |
| 游戏首页 | 继续最近一局、新开一局 | 状态卡、按钮、最近存档摘要 |
| 游戏主界面 | 三栏布局 | 完整 UI 设计稿和组件规范 |
| NPC 对话界面 | 玩家与 NPC 自由对话 | 气泡、头像、输入框、快捷行动 |
| NPC 档案抽屉 | 身份、玩家已知诉求、公开关系与已获线索 | 档案卡、标签；不得显示人物信任度或隐藏数值 |
| 地图面板 | 村庄地图和地点状态 | 地图底图、图层、高亮状态 |
| 事件卡片 | 固定事件、条件事件、突发事件 | 选项、故事日/剩余天数；仅服务端显式声明超时时显示现实时间倒计时 |
| 证据库 | 暗线线索和档案材料 | 文档缩略图、可信度标记 |
| 日终结算页 | 当日行动总结、夜间摘要 | 不含数字 delta 的体感回执、风险提示 |
| 结局页 | 主结局、亚结局、十四轴文字档位和终局台账 | 结局图、轴档位与台账排版；禁止综合评分 |
| 复盘页 | 时间线、关键决策、隐藏信息 | 曲线、时间线、日志卡 |
| 加载/错误页 | LLM 等待、资源缺失、网络错误 | 空状态、错误状态、重试按钮 |

### 7.2 主界面布局

第一版游戏主界面采用三栏布局：

```text
左侧状态栏：行动日、行动点、预算、核心指标、警报
中间对话区：NPC 回复、玩家输入、快捷行动、系统结算
右侧信息栏：地图、NPC 档案、事件日志、证据库
```

设计要求：

- 左侧强调“资源压力”。
- 中间强调“谈判与行动”。
- 右侧强调“信息研判”。
- 同屏必须能看到当前行动点、预算、目标 NPC 和最新风险。
- 不要把玩法说明做成大段文字墙。
- 五项体感指标只能显示无刻度进度条和当前文字档位；后果提示不得显示数值、涨跌量或可反推人物信任度的信息。状态区分仍需颜色、图标和文字三重编码，但颜色不能成为唯一信号。

### 7.3 组件清单

UI 组件必须覆盖：

- 主导航。
- 登录表单。
- 普通按钮、主要按钮、危险按钮、禁用按钮。
- 文本输入框。
- 自由对话输入区。
- 快捷行动按钮组。
- 行动点计数器。
- 预算条。
- 指标条。
- 风险徽标。
- NPC 头像按钮。
- NPC 档案卡。
- 关系标签。
- 事件卡。
- 证据卡。
- 地图图例。
- 夜间摘要卡。
- 系统日志条。
- 结局台账与十四轴档位卡（不含分数、星级或评级）。
- 复盘时间线。
- 弹窗和确认框。
- Toast 提示。
- 加载状态。
- 错误状态。
- 空状态。

## 8. NPC 美术需求

### 8.1 NPC 分类

NPC 视觉必须能区分以下类别：

| 类别 | 视觉识别点 |
|---|---|
| 村民 | 年龄、家庭处境、劳动痕迹、村庄生活背景 |
| 村干部 | 基层干部气质、夹在上下之间的压力 |
| 县级干部 | 正式、谨慎、会议和文件语境 |
| 企业方 | 商务感、项目推进压力、利益诉求 |
| 媒体 | 采访设备、独立调查或舆情传播气质 |
| 上级巡察组 | 严肃、程序性、审查感 |
| 暗线相关人物 | 不能一眼暴露反派身份，但要有可回看细节 |

### 8.1.1 每个人物必须单独做美术设定

当前文档不能只写“村民、干部、媒体”这种大类要求。第一版按 `art_need_arguments.md` 为玩家李致远、县委书记蒋崇岳、23 名主要 NPC 和 5 名配角分别制作人物设定，共 30 人。NPC 资源与剧本包稳定 `npc_id` 一一对应；玩家使用 `player_li_zhiyuan_portrait_*` 资产 ID、`linked_entity_type=player` 和 `linked_entity_id=player_li_zhiyuan`，不创建 NPCState。

每个人物至少需要明确：

- `npc_id`
- 中文显示名
- NPC 类型
- 年龄段
- 性别表达
- 社会身份
- 家庭/职业背景
- 性格视觉关键词
- 利益诉求视觉关键词
- 服装
- 发型
- 面部特征
- 姿态和眼神
- 常用随身物件
- 肖像背景
- 主色和辅助色
- 是否掌握暗线线索
- 暗线视觉暗示
- 禁止画法
- 第一版必须交付资源
- M2 情绪差分资源
- 对应 `asset_id`

```markdown
- 暗线视觉暗示：
- 禁止画法：
- 第一版资源：
- M2 情绪差分：
- 对应 asset_id：
```

### 8.1.2 人物设计与参考图风格的关系

所有人物必须与 `background/美术设计/设计参考/` 的 UI 和场景风格一致。

人物肖像统一要求：

- 半写实手绘水彩质感。
- 头肩像或胸像，放入档案卡片式边框。
- 光照柔和，不能有商业摄影棚强光感。
- 背景可出现低饱和村庄、河流、办公室、档案室或会议室元素。
- 线条和笔触要与手绘地图、旧纸 UI 匹配。
- 脸部要有年龄、劳作、压力、身份和性格痕迹。
- 服装要符合县域基层治理语境，例如旧夹克、衬衫、基层干部外套、工作服、采访马甲、商务外套等。
- 配饰要克制，例如文件夹、搪瓷杯、老式手机、账本、录音笔、采访本、红章文件。

禁止：

- 用真实照片滤镜化。
- 把所有村民画成同一张脸。
- 把干部全部画成同一种西装形象。
- 把暗线人物画成明显反派。
- 把女性角色过度美化或网红化。
- 使用与参考图冲突的高饱和赛博色、二次元大眼、手游卡牌光效。

### 8.2 头像规格

第一版每个可对话 NPC 至少需要一张中性头像。

推荐规格：

| 用途 | 尺寸 | 格式 | 背景 |
|---|---:|---|---|
| 源文件 | 2048x2048 | PSD/AI/源格式 | 分层 |
| 游戏头像 | 512x512 | WebP/PNG | 透明或统一底 |
| 小头像 | 128x128 | WebP/PNG | 透明或统一底 |
| 复盘头像 | 256x256 | WebP/PNG | 透明或统一底 |

构图要求：

- 头肩像。
- 正面或 3/4 侧面。
- 眼神方向统一。
- 安全区域内脸部不能被 UI 裁切。
- 不使用真实人物肖像。

### 8.3 情绪差分

建议支持以下情绪状态：

```text
neutral
trust
tense
angry
worried
resistant
relieved
```

第一版最低要求：

- `neutral`

M2 建议补齐：

- `tense`
- `angry`
- `trust`
- `worried`

技术映射：

| 服务端玩家可见 `portrait_state` | 优先头像 |
|---|---|
| `trust` | `trust` |
| `worried` | `worried` |
| `resistant` | `resistant` |
| `angry` | `angry` |

### 8.4 角色差异化要求

每个 NPC 头像必须体现：

- 年龄段。
- 社会身份。
- 家庭或职业背景。
- 性格倾向。
- 与搬迁事件的关系。
- 与玩家已知职业和公开经历相符的随身物件；不得用服装、光影或道具提前暗示尚未解锁的暗线线索。

注意：

- 不能把暗线人物画得过于脸谱化。
- 同村村民之间要有亲缘、邻里、年龄和经济状态差异。
- 干部类角色要区分基层干部、县级领导、职能部门和巡察组。

### 8.5 不同人物类型的细化设计要求

#### 8.5.1 村民类

村民是搬迁动员的主要对象，人物设计必须有生活质感，不能只是“普通农民”符号。

需要区分：

- 年长村民：皱纹、旧衣、保守、土地和祖坟牵挂。
- 中年户主：家庭压力、补偿谈判、务工或务农痕迹。
- 外出务工家庭代表：衣着更城市化，但与村庄仍有联系。
- 意见领袖：眼神更直接，姿态更稳，有被他人依赖的气场。
- 钉子户：防御感强，但不能画成坏人；要体现其真实诉求和软肋。
- 已配合村民：相对放松，但仍保留现实顾虑。
- 摇摆户：表情犹豫，视觉上兼有期待和警惕。

常用视觉元素：

- 旧夹克、深色衬衫、毛衣、草帽、雨靴、劳作手套。
- 老式手机、账本、补偿通知、家庭照片、药袋。
- 背景可出现院落、山地、河边、村道、老屋门口。

#### 8.5.2 村干部和基层干部类

村干部和基层干部要体现“夹在上级任务和村民关系之间”的压力。

视觉要点：

- 衣着比普通村民更正式，但不能像城市精英。
- 可使用夹克、衬衫、工作证、文件袋、笔记本。
- 表情常带疲惫、谨慎、圆滑或防御。
- 背景可用村委会、会议室、档案柜、宣传栏。

需要区分：

- 真心推进工作的干部。
- 消极推诿的干部。
- 与暗线有关但表面正常的干部。
- 被上下压力裹挟的干部。

#### 8.5.3 县级干部和职能部门类

县级干部和职能部门人员要体现程序性、政务感和责任边界。

视觉要点：

- 更整洁的衬衫、夹克或行政外套。
- 文件、会议材料、办公室背景。
- 表情克制，不夸张。
- 与基层干部相比更强调制度身份和审慎态度。

#### 8.5.4 企业方

企业方必须体现项目推进、成本控制和利益诉求，但不能画成脸谱化反派。

视觉要点：

- 商务夹克、衬衫、工地安全帽或项目资料。
- 背景可用拟建厂区、项目沙盘、办公室、合同文件。
- 表情应体现自信、急迫、算计或防守。
- 暗线相关企业角色可以通过文件包、遮掩资料、回避眼神体现，但不能直接画成阴谋形象。

#### 8.5.5 媒体类

媒体角色要体现信息传播和调查压力。

视觉要点：

- 采访本、录音笔、相机、手机、工作马甲。
- 表情更敏锐，眼神有观察感。
- 背景可用采访现场、村道、办公室门口。
- 不同媒体角色要区分独立调查、追热点、受引导或被利用等状态。

#### 8.5.6 上级巡察组和监督角色

巡察组要体现程序性审查和外部压力。

视觉要点：

- 正式、克制、低情绪。
- 文件夹、检查表、证件、会议桌。
- 眼神审慎，不要过度威严化。
- 与县级干部相比更有距离感和审查感。

每个状态必须提供视觉规则：

- 颜色。
- 图标。
- 边框或描边。
- 悬停状态。
- 选中状态。

## 17. 动效建议

第一版不强制复杂动效，但建议定义轻量动效规则：

- 五项体感指标发生玩家可见档位变化：短暂颜色和方向提示，不显示数值或 delta；暗档、人物信任度和未跨档变化不播放升降动效。
- 风险升高：卡片边缘闪烁一次，不循环干扰。
- 新事件出现：事件卡滑入。
- 日夜切换：低成本遮罩过渡。
- 地图地点状态变化：描边或标记变化。
- LLM 等待：低频加载动画。

动效不得影响可读性，也不得让玩家误以为状态已提交。状态以服务端返回结果为准。

## 20. 前端调用规则

前端不得直接写死图片路径，应通过以下流程加载：

```text
读取 session.package_id + package_content_hash
  ↓
GET /api/game/session/{session_id}/assets-manifest
  ↓
按 asset_id / linked_entity_id / usage 查询资源
  ↓
存在目标状态资源则使用
  ↓
不存在则使用 fallback_asset_id
  ↓
仍不存在则使用 system_missing_asset
```

该接口由服务端校验当前账号的 session 所有权，并按 session 锁定的内容哈希读取不可变包。前端缓存键至少包含 `package_content_hash + asset_id + asset.version`，禁止同名 `asset_id` 被另一个包的资源覆盖。

### 20.1 NPC 头像选择

```text
target emotion asset
  ↓ 不存在
neutral portrait
  ↓ 不存在
npc_unknown_portrait_neutral
  ↓ 不存在
system_missing_asset
```

### 20.2 地图状态选择

地图底图和交互图层分离：

- 底图由 `map_base` 资源提供。
- 可点击对象由 `map_layers.json` 提供。
- 状态颜色和图标由前端根据服务端 `PlayerVisibleDTO.map_visual_state`、一次性 `newly_unlocked` 提示和 design tokens 渲染；不得读取隐藏 NPC 状态自行推导。

### 20.3 事件图选择

```text
event_id exact asset
  ↓ 不存在
event category default
  ↓ 不存在
scene fallback
  ↓ 不存在
system_missing_asset
```

## 23. 与剧本机会模型的交付对齐

美术资源不仅服务“页面好看”，还必须让玩家清楚知道当前能见谁、能去哪里、因何暂时不能继续推进。每个 `interaction_opportunity` 至少要能被一种视觉入口承载：地图位置、NPC 档案状态、任务/来访卡、电话或档案线索入口。

### 23.1 入口状态规范

以下状态由前端根据剧本包和运行时数据渲染，美术需提供图标、描边、底纹或组件状态，不应把状态文字直接烘焙进角色肖像或地图底图：

| 运行时状态 | 玩家含义 | 视觉要求 |
|---|---|---|
| `available` | 当前可互动 | 档案夹/地图对象有低调高亮与可点击状态 |
| `newly_unlocked` | 因证据、事件或关系新开放 | 提供一次性提示标记，阅读后可消失 |
| `locked` | 当前不能互动 | 可见但弱化；前端展示剧本提供的非剧透原因 |
| `cooldown` | 刚互动过，暂时不可再约谈 | 时间/日程标记，避免使用失败或禁止色误导 |
| `event_active` | 当前有玩家可见事件占用或影响该入口 | 使用事件标记；具体风险只展示剧本提供的非剧透公开文案 |
| `completed` | 当前机会已处理或由其他剧情关闭 | 档案/地点保留历史痕迹，不从地图无故消失 |

其中 `available`、`locked`、`cooldown`、`completed`、`event_active` 属于 `map_visual_state` 主状态；`newly_unlocked` 是服务端返回的一次性提示布尔值，不与主状态互斥，也不得由前端自行推导。

### 23.2 剧本对象到美术对象的映射

美术负责人在角色名单和事件清单冻结后，必须输出 `art_story_mapping.json`，由技术侧在发布剧本包时校验。它不替代 `assets_manifest.json`，只描述叙事对象与视觉入口的关系。

### 23.3 交付验收补充

在既有美术验收外，还必须检查：

- 每个最终可对话 NPC 有中性肖像、档案入口和至少一个可定位的互动入口。
- 每个关键事件、线索和地点都有可用资源或明确 fallback。
- `art_story_mapping.json` 中的所有 ID 能在剧本包和 `assets_manifest.json` 中解析。
- 解锁、锁定、冷却、风险、完成状态在参考图的政务档案式风格内可区分，且不单靠颜色。
- 美术更新不会改变已发布 package 中的 `asset_id` 含义；新版本以新 package 发布，保证旧存档仍可正确显示。
