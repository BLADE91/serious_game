# 玩家体验报告：四项行动、红头文件与逐户签约重构

## 1. 验收范围与方法

本报告基于两类验证：

1. 通过公开游戏API，以玩家身份从D1连续推进至D90，不直接修改存档，不跳过强制决策；
2. 对四项行动、班子会议、红头文件、代表户合同批次、独立签约人与资源结算执行专项端到端测试。

完整流程采用偏公开、核查、依法推进的稳定路线，共处理76次剧情决策。实跑结果为：到达D90、正常结束、无流程阻塞。

## 2. 已达到的体验目标

| 项目 | 玩家实际感受 | 结算闭环 |
|---|---|---|
| 固定县长身份 | 新档直接进入剧情，不再选择技术派、基层派等出身，也不再出现“若你是……”旁白 | 服务端固定使用无属性修正的县长身份；旧客户端提交出身字段也不会改变身份 |
| 四项基础行动 | 行动目录只显示入户走访、干部访谈、班子会议、查阅档案 | 分别消耗1、2、2、1点行动点；剧情决策和剧情专属程序不再作为常驻行动展示 |
| 档案取得 | 开局可见项目简报、36户底账、资源台账和已公示补偿方案；新线索必须由剧情或具体谈话取得 | 档案保存来源、取得日期、取得行为、证据等级和保密范围 |
| 班子会议 | 玩家公开发言对全部参会NPC可见，每名NPC可分别回应并形成自己的表态 | 会议保存完整公开转录、表态、决议、责任人、期限和会议纪要 |
| 红头文件 | 开局已有上级批准并公示的补偿方案；新增文件必须先有会议决议 | 决议通过后由文书LLM起草，玩家可修改；必要NPC会签后才能签发、归档和公示；文件只设政策与资源授权上限，不占用具体资源 |
| 证据等级 | 不再只是档案标签 | E1可支撑一般通知或调查启动；医疗、迁坟等文件至少需要E2；补偿调整至少需要E3 |
| 代表人发起合同 | 向周大山明确提出逐户发合同时，先出现批次确认 | 周大山层生成6份合同：周大山本人1份，另外5户各1份；6个独立签约人，不能代签 |
| 合同审校与审阅 | 合同先经独立专业审校，再由本户签约人决定接受、拒绝、要求说明或提出反报价 | 审校模型逐项指出问题字段、正文位置、原因和修改建议；未通过不得送给NPC；NPC立场仍由本户签约人角色LLM判断 |
| 资源调用 | 合同必须先填写现金、预算信封、房源、服务名额和履行日期 | 送审时预占2个游戏日；签署后转为承诺；到期才支付或交付；失败、过期会释放或记录违约 |
| 真实签约户数 | 剧情选项不能再凭空增加签约户数 | 只有本户签约人接受、玩家确认签署且资源预占有效的逐户合同可以增加1户 |

## 3. 资源与一致性检查

当前结构化资源已经闭合：

- 可支配预算7800万元，分为房地补偿、安置交付、搬迁过渡奖励、附属物与经营迁坟、医疗就业就学、调查法务公开和风险预备金七个信封；
- 安置房按D1、D30、D60三期配置，共36套；
- 医疗资源包括血铅复检、儿童综合评估和紧急转诊；
- 民生资源包括就学衔接、稳定就业、职业培训、小微经营恢复、创业贴息和迁坟事务服务；
- 初始补偿方案明确房屋结构、宅基地、承包地、搬迁费、过渡费和公开窗口奖励的计算标准。

本轮修复了三类重大一致性冲突：

1. 旧剧情节点过去会直接写入真实签约户数。现在全剧本包不再登记任何“某户已入账”“某户已签”类剧情旗标，全部改为“核心矛盾已缓解”“补账已核验”等谈判里程碑。框架层还会统一拦截漏网的“已入账/已签”旗标，防止旧内容重新污染合同权威台账。
2. 31户过去挂着未登记、正常流程无法取得的`flag_*`签约门槛，测试只能靠直接改存档通过。现在这些伪门槛已经删除；一般家庭由结构化合同条件和本户签约人审阅决定是否接受。谭老六、袁桂兰仍保留真实剧情门槛，因为两户确有必须先处理的旧账矛盾。
3. 会议决议过去混淆了“政策授权”与“具体占用”。现在红头文件只能采用`authorization_ceiling`：它规定某类资源最多允许用于什么对象、多少数量和什么期限，但签发、归档、公示均不改变资源可用量。只有引用该文件的逐户合同被NPC接受，或形成具有具体对象的执行凭证时，才按文件剩余授权额度与实时资源库存进行原子校验和占用。

预算写入也已从“内容作者自觉遵守”改为强制来源规则：

| 结算来源 | 是否允许改变预算 | 必须记录的来源 |
|---|---:|---|
| 普通单人或多人对话 | 否 | 配置中误写预算会被拒绝 |
| NPC夜间交流 | 否 | 配置装载和运行时双重拒绝 |
| NPC夜间行动 | 否 | 配置装载和运行时双重拒绝 |
| 玩家明确选择 | 是 | 决策ID与选项ID |
| 玩家明确资源行动 | 是 | 客户端行动ID与行动定义ID |
| 已签合同 | 是 | 合同ID；先形成承诺，不立即支付 |
| 合同履约 | 是 | 合同ID与付款或交付节点 |

因此，任何游戏开始后的预算变化都能回答“是哪一个玩家选择、哪一个玩家行动，或者哪份合同的哪一个履约节点造成的”。初始7800万元是开局红头文件已经确认的可支配余额，另有200万元前期协调费作为开局既成支付，不属于玩家进入游戏后的变化。

预算总览现在同时显示“账面余额”和“可再支配余额”。后者直接扣除所有有效的合同预占和已签未付承诺，不再使用`累计承诺－累计支付`推算。红头文件授权额度单独显示“授权、已调用、剩余”，不从可再支配余额中重复扣除。这样开局既成支付200万元不会抵消后来合同的承诺，任何剧情选择或资源行动也不能花掉已经答应给某户的资金。

## 4. 疲劳结算的实际体验

当前规则已经实现，且不存在主动“休息一天”选项：

- 当日消耗0至3点且不加班：疲劳减5；
- 消耗4至5点：疲劳不变；
- 消耗6至7点：疲劳加1；
- 消耗8点：疲劳加3；
- 加班额外增加`5 + 8 × 加班点数`疲劳；
- 章节切换额外减10；
- 疲劳达到25、50、75后，次日行动点上限依次降为7、6、5；
- 连续3天满负荷后，次日上限最多为6。

但完整实跑暴露出体验问题：如果玩家只处理免费剧情决策并不断结束当天，绝大多数日期都不花行动点，疲劳会长期保持“精神尚可”。规则本身有效，但主流程对自主行动的需求太低，使疲劳几乎没有博弈意义。

## 6. 优化方向：把资源预占变成玩家可理解的博弈

短期预占应当保留，但必须让玩家清楚它不是付款，也不是签约成功。当前后端状态已经拆成下列五步：

| 合同阶段 | 资源状态 | 预算余额 | 玩家应看到的文案 | 后续结果 |
|---|---|---:|---|---|
| 草案编辑 | 未预占 | 不变 | 未预占 | 可修改条款，不影响其他合同 |
| NPC拒绝、要求说明或反报价 | 未预占 | 不变 | 未预占 | 原有短期预占立即释放 |
| NPC接受 | 短期预占两天 | 不变 | `预占至D×，尚未支付` | 玩家必须在到期前确认签署；到期自动释放 |
| 玩家确认签署 | 转为合同承诺 | 不变 | 已签署并占用资源，尚未支付 | 该房源、服务名额和预算信封不能再被其他合同使用 |
| 到达合同付款或交付日 | 已支付或已交付 | 付款日才减少 | 已支付／已完成交付 | 写入合同ID和具体履约节点 |

这个区分会产生真正的谈判压力：玩家可以同时推进多户，但不能无限占着稀缺房源；某户接受后，玩家只有两天决定是否锁定资源；选择高规格房源或稀缺医疗名额，会直接压缩其他户的可谈空间。关键是代价必须公开，不能让玩家在看不到预占状态的情况下被系统暗中扣掉选择权。

建议终端和未来图形界面增加三个相互联动的区域：

1. **合同卡片**：始终显示本户状态、预占截止日、尚未支付金额、占用房源和服务名额；临近到期时在D×早晨卡片中提醒。
2. **资源总览**：对每个预算信封、房源和服务名额分别显示“可用、预占、已承诺、已支付或已交付”，不能继续用一个含义模糊的“已使用”合计替代。
3. **资源流水**：按时间显示来源类型、选择ID或合同ID、资源、变动前后值、付款状态和履约节点；点击合同ID可以回到合同正文和签署档案。

为了让这套机制形成博弈而不是纯表格管理，后续剧情应围绕资源冲突出题。例如两户都要求同一套低楼层无障碍房时，玩家可以先谈其中一户、召开班子会议新增可替代资源、调整交付期限，或承担某一户预占过期后立场恶化的风险。NPC只应根据自己能知道的公示文件、合同条款和可见资源作出反应，不能凭内部台账“读心”。

还需要避免两个反体验设计：

- 不增加“一键批量签约”。可以复用政策基准草案以减少录入，但每户条款、审阅、接受和玩家确认仍然独立。
- 不把预占做成永久锁。拒绝、反报价、要求说明、玩家重拟条款和到期都必须释放，并在流水中说明释放原因。

这一优化方向的验收标准应是：玩家在任何时刻都能用一张资源总览回答“还有什么可谈”，用一张合同卡回答“这户已经走到哪一步”，用一条流水回答“为什么资源变少了”。

## 7. 本轮 comments 修复后的玩家体验

本轮针对审查意见补齐了五个会破坏玩家理解或台账一致性的缺口：

| 原问题 | 修复后的规则 | 玩家可感知结果 |
|---|---|---|
| 红头文件错误占用具体资源 | 文件只登记政策权限和资源授权上限；签发、公示不再预占房源、服务或预算 | 玩家可以先完成合法政策程序，具体稀缺资源仍留到逐户合同中竞争；文件总览显示授权、已调用、剩余 |
| 治理行动可能卡住整局 | 进行中的行动可显式中止；讨论中的班子会议同步标记为未通过；普通菜单和命令模式都有恢复入口 | 错误选择、空输入或中断流程不会迫使玩家弃档 |
| 无关输入仍会触发材料和签约副作用 | 入户走访、干部访谈在任何NPC回复和档案生成前统一审查；无关内容只返回“请输入与本游戏相关的话语” | 玩家无法靠输入无关文字刷材料、解锁拟约或改变关系 |
| 正文可私自增加结构化附件之外的资源承诺 | 每次生成或编辑合同都调用独立的专业合同审校模型，并叠加确定性规则核验；未通过不得送给NPC | UI逐条显示问题字段、对应原文位置、风险说明和修改建议，玩家知道改哪里，而不是只收到笼统的“合同非法” |
| 合同每次重拟会丢失NPC上轮意见 | 每户合同保留最近8次审阅结论、理由和反报价，并随存档持久化，再次送审时传给同一签约NPC | NPC不会刚提出说明要求，下一轮就像从未谈过一样重新判断 |

第二轮 comments 又对合同审校和终端操作完成了五项收口：

| comments问题 | 已实现规则 | 玩家可感知结果 |
|---|---|---|
| 审校可能返回“不通过”却不给具体问题 | `reject`或`needs_revision`必须至少包含一项带原文位置的问题，否则整个模型响应按非法响应处理 | 不会再出现“禁止送审”与“未发现问题”同时显示 |
| 金额与日期使用普通子串匹配 | 现金必须以“数值+万元”出现在现金条款中；付款、搬离、交房日期必须分别出现在对应语境中 | `D10`不会再被误当成现金金额10万元，三个相同日期也不会互相冒充 |
| 完整合同只能单行编辑 | 终端提供多行合同编辑，单独输入“完成”提交、“取消”返回 | 玩家可以保留合同段落和条款结构，不会把第二行误当成命令 |
| 一个字段出错就丢失整张表单 | 后端错误在合同流程内部展示；已填条款保留，玩家选择需要修改的字段后原地重试 | 填错金额、日期或文件时不必重新录入全部条件 |
| UI大量暴露内部字段和资源ID | 审校字段、问题类别、预算科目、服务资源和批准文件改用中文业务名称与编号选择 | 玩家主要面对“现金补偿额、付款日、就学衔接”等业务概念，而不是`cash_amount`或资源ID |

第三轮审查进一步修复了上述实现的异常边界：

- 只有`ACTION_UNAVAILABLE`这类可通过修改条款解决的业务错误留在合同表单；状态版本冲突、账户权限、认证、网络和模型故障回到全局恢复流程；
- 命中历史审校缓存时重新执行当前结构契约，旧版“不通过但无问题”缓存会被忽略并重新调用专业审校模型；
- 现金金额必须位于“现金补偿、现金权益、补偿款、补偿金额或支付现金”语境中，违约金等其他金额不能冒充核心补偿额；
- 条款尚未成功保存时，退出入口明确提示“本次未通过内容不会保存”；
- `minimum`、`submitted`等后端错误详情分别显示为“政策最低补偿额”“本次填写金额”。

第四轮审查补齐了四个更隐蔽的失败场景：

| comments问题 | 已实现规则 | 玩家可感知结果 |
|---|---|---|
| “非现金补偿10万元”可能被金额规则误认成现金条款 | 确定性核验排除“非现金补偿”“非现金补偿款”和“不支付现金”等否定语境；专业模型继续负责更复杂的自然语言歧义 | 合同不会因为写了同一个数字就错误通过，结构化现金额必须在正文中形成真实、肯定的现金承诺 |
| 通用`PERMISSION_DENIED`被当作可编辑条款错误 | 缺少标准外补偿批准文件改为明确的`ACTION_UNAVAILABLE`；真正的账户权限错误立即交回全局错误处理 | 玩家可修改的合同问题留在表单，账号无权或鉴权失败不会伪装成“再改一个字段即可” |
| 失效历史审校缓存仍占用本局模型调用额度 | 旧缓存先按当前契约复核；确认失效后，本次刷新预算计算排除该条历史记录，新的有效审校仍正常记账 | 即使调用额度只剩一次，玩家也不会因为系统自己的旧坏缓存而无法重新审校 |
| 专业审校暂时不可用会丢失整张合同表单 | 模型不可用或返回非法结构时，无论是初次生成还是玩家修改完整正文，终端都保留本次输入，说明尚未写入草案，并允许原地重新审校或明确退出 | 临时模型故障不再迫使玩家重填金额、房源、服务、日期或多行合同正文；状态冲突等不安全重试仍走全局恢复 |

终端普通菜单此前只列出旧的资源行动，四项治理行动实际上主要依赖命令模式。本轮一并修正：菜单现在同时识别`governance`与`resource_action`，并提供“治理、资源与进行中的行动”入口。玩家能在同一入口查看占用、行政文件、逐户合同及卡住的治理行动，并选择中止。

红头文件的玩家修改权也已落实到实际终端路径：`document <文件ID>`先展示标题、版本和完整正文，玩家可以保持原文或用多行编辑器提交修改；修改通过会议决议一致性校验后生成新版本，并清空此前会签，再由全部必要NPC重新会签。终端不会再跳过正文确认直接代玩家进入会签。

这些修复没有改变短期合同预占原则：NPC接受后才预占，签署前不支付；玩家确认签署时必须再次通过资源校验并把预占转为合同承诺。红头文件不再锁资源，而是约束后续合同最多能调用多少；合同引用批准文件时，系统同时核验文件状态、授权剩余额度和实时资源可用量。终端不再静默引用全部文件，玩家必须明确选择本合同引用的批准文件。

## 8. 总体评价

规则层和终端入口现在都形成了完整、可审计的闭环：权限决定能做什么，四项行动建立场景，档案提供有来源的信息，会议形成决议，红头文件建立政策与授权上限，专业审校模型阻止合同文本越权，合同接受后调用并锁定资源，签署与履约再写入真实台账。终端的`do`命令已按`governance`模式分流，不再把四项行动误送到旧资源报价入口；`governance`、`contract`和`document`命令能分别查看总览、处理逐户合同和完成会签签发公示。

当前最大的体验风险已经从“后端没有结算、终端无法进入”转为“主剧情对签约压力的反馈仍不够连续”。D90零签约直接失败是合法路线，不需要由系统强行阻止；但下一轮应让关键日期明确反馈当前进度、剩余资源和失败风险，使玩家是在知情情况下选择承担失败，而不是到结局才第一次得知后果。
