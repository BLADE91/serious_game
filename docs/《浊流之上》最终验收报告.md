## 五、会议与红头文件对游戏体验的影响

红头文件不是单纯的文本奖励，而是把玩家口头态度变成正式治理责任的机制：

1. 玩家先决定会议议题、材料和参与者。
2. AI 成员从赞成、有条件赞成、反对或弃权中作出立场选择，再表达理由。
3. 引擎根据成员选择形成会议决议，不由 AI 自由制造业务结果。
4. 规则层检查文种、对象、责任人、期限、资源和公开范围。
5. 审校通过后会签并成文，成为后续剧情、人物记忆和复盘可引用的权威记录。

其体验价值在于：玩家不能只靠一句承诺安抚所有人，而必须决定是否把承诺写进正式制度。成文会提高执行确定性和责任可追溯性，但也会减少后续回旋空间，并可能暴露材料矛盾、资源不足或责任风险。这构成“政治承诺”和“行政责任”之间的博弈。

当前完整成文流程已有截图和真实调用证据；建议人工验收时特别观察：材料不足时按钮为何不可用、成员反对是否容易理解、成文后的影响是否在次日简报和复盘中足够明显。

## 六、逻辑与内容问题记录

### 已解决或已有自动化保护

- D1 开场使用 36 户，30 户仅作为后续签约目标线。
- 五份卷宗的数量和顺序保持一致。
- 人物是否出现由剧情揭示和合法机会控制，不再仅因角色存在于数据包就提前显示。
- 会谈开始但未发言退出不扣精力；首次成功交流才原子扣点。
- 合同仅在相关人物或代表会谈中出现，签署后立即计入进度。
- 地图入口锁定点击地点，伪造地点不能产生部分提交。
- 线索均具有至少一条合法获取方式，未来线索不提前泄露。
- 决策展示受剧情铺垫门槛约束，保存载入后不能直接跳过铺垫。
- 通晓币公告和 API 配置界面已进入前端流程。

### 尚待确认或修复

1. **D70 夜间触发不稳定（P1）**：合法推进在特定策略状态下未创建强制会谈，应检查 v3 触发条件、候选状态和先前会谈归档对条件的影响。
2. **D84 夜间矩阵未验收（P1）**：四种话术均缺少本轮真实证据，不能仅凭自动化内容契约判定通过。
3. **NPC 状态与表达偶发不一致（P1/P2）**：`settle` 后的台词仍可能继续追问；应限制表达任务只能表述“暂时接受、保留意见或停止主动追问”。
4. **WU-04 合同偶发非 2xx（P1 待复现）**：主流程通过，但恢复运行出现一次异常，需单独以真实 API 重签 WU-04 并保存网络日志。
5. **会议决议按钮偶发不可用（P1 待复现）**：需确认是材料、发言完成状态还是前端刷新问题，并给玩家清楚的阻断原因。
6. **失败重试会刷新顶层 `updated_at`（P2）**：业务状态和版本未变化，但失败请求可能改变元数据时间；不影响主要玩法，但不利于严格失败原子性审计。
7. **D90 后取证弹窗阻挡（验收工具 P2）**：浏览器脚本应先处理进度播报再采集结局后页面，不是已确认的玩家流程阻断。
8. **移动端重点页面需要人工视觉复核（P2）**：已有 390×844 截图和零横向溢出数据，但仍需人工检查夜间长对话、合同长表单和会议长文本的阅读舒适度。
