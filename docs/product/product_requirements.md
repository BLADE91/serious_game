# 严肃游戏产品需求文档

## 1. 文档定位

本文档定义严肃游戏从“剧本生成器”升级为“可运行治理模拟游戏”的产品需求。当前剧本属于初级版本，后续会持续修改、扩写和替换。系统必须把剧本视为可版本化、可重抽取、可校验的内容资产，不能把当前剧本中的具体人物、地名、章节数量、事件数量写死在代码中。

本文档与以下既有文档配合使用：

- `README.md`：当前剧本生成管线说明。
- `需求清单.md`：完整玩法、NPC、指标、前端和研究数据要求。
- `docs/game_design/script_quality_standard.md`：剧本质量标准。
- `docs/task_daytime_action_module.md`：白天行动模块最小任务。
- `docs/task_event_and_night_simulation_module.md`：事件与夜间推演模块最小任务。

## 2. 产品目标

系统目标是构建一个面向基层治理、公共管理教学和行为研究的严肃游戏平台。

第一阶段目标是单人玩家版本。玩家扮演地方治理决策者，在有限时间、预算和行动点约束下，与多个 LLM NPC 和规则驱动 NPC 互动，推动生态搬迁任务，同时处理舆情、信访、干部执行、暗线调查和上级考核。

第二阶段目标是研究平台版本。系统支持完整行为日志、剧本版本管理、NPC 版本管理、实验条件分组、数据导出和复盘分析。

第三阶段目标是多人或人机混合版本。不同玩家可扮演不同治理角色，未被真人扮演的角色由 LLM Agent 补位。

## 3. 核心原则

1. 剧本可变，规则稳定。  
   当前剧本只是内容样例。代码只依赖结构化字段、规则表、变量表和 NPC 档案，不依赖具体文本。

2. LLM 角色评估，系统校验提交。  
   NPC 指标变化的核心来源是目标 NPC 的 LLM 基于自身人设、角色规则、上下文、记忆和玩家说服文本做出的态度评估。LLM 必须输出固定结构的数据，例如 JSON。系统负责校验、裁剪、审计和提交结果。行动点、预算、事件触发、结局判定和非法行为拒绝仍由系统规则执行。

3. 玩家自由表达，系统严格结算。  
   玩家与 NPC 的主要互动方式是输入文字进行说服。系统可以解析玩家意图并检查行动是否合法，但不能用固定选项或固定数值表替代 NPC LLM 对“是否被说服、态度如何变化”的判断。

4. 研究数据完整。  
   系统必须保存完整行动、对话、状态快照、事件、夜间隐藏互动和结局数据，保证后续可复盘、可导出、可分析。

5. 内容版本隔离。  
   新剧本、新 NPC 档案、新规则参数只影响新开局。已开始的游戏必须继续使用开局时锁定的版本。

## 4. 用户角色

### 4.1 玩家

玩家在游戏中承担治理决策角色。玩家通过对话、行动选择和政策工具使用推进任务。玩家看不到全部隐藏状态，只能通过走访、谈判、调研、档案、媒体和干部沟通逐步获得信息。

### 4.2 内容编辑

内容编辑负责修改剧本、NPC 档案、事件文本、结局文本、行动工具和数值参数。内容编辑需要可视化查看剧本结构、局部修改内容、重新抽取 JSON 和运行校验。

### 4.3 研究者

研究者负责设置实验条件、查看行为日志、导出数据、比较不同剧本版本和 NPC 版本的影响。研究者需要能区分正式局、测试局和沙盒局。

### 4.4 管理员

管理员负责模型配置、API Key、运行成本、数据备份、用户管理和系统健康状态。

## 5. 游戏范围

### 5.1 第一阶段必须支持

- 单人玩家。
- 最小账号登录系统。
- 90 个行动日。
- 每日 3 个行动点。
- 可选择加班获得额外 1 个行动点，并产生副作用。
- 预算初始 8000 万元。
- 至少 36 个 NPC 的结构化档案。
- 白天玩家行动。
- 夜间 NPC 自主互动摘要。
- 事件触发。
- 存档和读档。
- 结局判定。
- 复盘页。

### 5.2 第一阶段暂不强制支持

- 多人实时协作。
- 移动端适配。
- 语音输入和语音输出。
- 真实地图 API。
- 复杂 3D 场景。
- 大规模在线并发。
- 注册审批、找回密码、角色权限、组织管理、第三方登录和复杂用户后台。

## 6. 核心游戏循环

单个行动日的标准流程如下：

1. 系统展示当日状态、行动点、预算、核心指标和可见事件。
2. 玩家选择目标 NPC、地点、档案或事件。
3. 玩家以文字输入方式对目标 NPC 进行说服、谈判、追问或承诺；快捷行动只能作为辅助入口。
4. 行动解析器把玩家输入辅助归类为结构化行动，但保留完整原文。
5. 合规检查器判断行动是否允许。
6. 行动服务扣除行动点和预算，并生成玩家行动上下文。
7. NPC 状态评估服务把玩家原文、行动上下文、NPC 人设、NPC 规则、记忆和世界状态传给目标 NPC 的 LLM。
8. 目标 NPC 的 LLM 判断本次说服对自己的信任、态度、焦虑、签约意向和风险行为的影响，并输出结构化 JSON。
9. 系统校验 LLM 输出的指标变化，合法后提交到状态。
10. NPC 对话服务生成符合角色和状态的回应。
11. 行动点耗尽后，玩家进入日终结算。
12. 事件服务检查固定事件、条件事件和风险事件。
13. 夜间推演服务执行 NPC 之间的信息传播、串联、阈值变化和隐藏行动。
14. 系统生成次日玩家可见摘要。
15. 系统保存完整状态快照。

## 7. 功能需求

### 7.1 剧本与规则版本管理

系统必须支持多个剧本版本。每个版本至少包含：

- 剧本 Markdown 母稿。
- 结构化 JSON。
- NPC 档案。
- 行动规则表。
- 事件规则表。
- 结局规则表。
- Prompt 版本。
- 模型配置版本。

新开局时，系统把这些版本锁定到 `session_id`。游戏过程中编辑剧本不影响已有局。

### 7.2 账号登录

第一阶段需要做一个最小账号系统。系统用于区分测试者、绑定存档和保护本地或服务器上的游戏数据。

必须支持：

- 用户名和密码登录。
- 密码哈希存储，禁止明文保存密码。
- MySQL 数据库存储账号信息。
- 登录后创建服务端会话或访问令牌。
- 游戏 session 绑定到账号。
- 用户只能查看和继续自己的存档。
- 管理员账号可以查看全部测试存档，第一阶段可用配置或种子脚本创建。

第一阶段暂不支持：

- 自助注册审批。
- 找回密码。
- 邮箱或短信验证。
- 第三方 OAuth 登录。
- 细粒度权限系统。
- 多组织和班级管理。
- 登录失败锁定、风控和设备管理。

后续需要补全：

- 账号角色：玩家、内容编辑、研究者、管理员。
- 权限表和接口级鉴权。
- 密码重置流程。
- 操作审计日志。
- 用户匿名化导出规则。
- 研究实验分组与账号绑定。

### 7.3 白天行动

第一阶段至少实现以下行动：

| 行动 | 行动点 | 目标 | 主要效果 |
|---|---:|---|---|
| 入户走访 | 1 | 村民 | 提升信任，获得信息，可能发现诉求 |
| 干部私谈 | 1 | 干部 | 获取过滤后的信息，影响干部执行力 |
| 调阅档案 | 1 | 档案或部门 | 解锁事实、证据或历史矛盾 |
| 提高补偿 | 1 | 村民或群体 | 消耗预算，改变心理底价和公平感 |
| 公开承诺 | 1 | 群体 | 提升短期信任，未兑现时产生强惩罚 |
| 接待媒体 | 2 | 媒体 | 影响舆情压力和报道方向 |
| 接待巡视组 | 2 | 外部监督 | 降低随机抽查失控概率，但消耗资源 |
| 加班协调 | 0 | 自身/干部 | 获得额外行动点，降低干部执行力或政治信用 |

所有行动必须输出：

- 新的 `GameState`。
- 新的目标 `NPCState`。
- LLM 输出的结构化指标变化。
- 指标变化的校验结果。
- `SimulationLog`。
- 风险提示。
- 对玩家可见的结算文本。

### 7.4 行动合法性

系统必须拒绝以下行为：

- 承诺超出预算或规则上限的补偿。
- 威胁、拘禁、恐吓、人身限制。
- 未走法定程序的强制拆迁。
- 伪造档案、伪造签名、伪造上级批示。
- 要求 NPC 透露超出其知识边界的信息。
- 让 LLM 绕过结构化输出直接改变游戏状态。

拒绝时，系统应给出自然语言提示，并说明可替代行动。

### 7.5 NPC 对话

每个 NPC 必须有：

- 基础身份。
- 诉求结构。
- 心理底价。
- 核心红线。
- 大五人格或等价性格参数。
- 语言风格。
- 知识边界。
- 信息可信度规则。
- 社会关系。
- 夜间联系人。
- 隐藏信息。
- 态度转变条件。

NPC 回复必须满足：

- 不说出自己不知道的信息。
- 不主动暴露底价和秘密。
- 不越权承诺系统规则之外的事。
- 不擅自改变签约、预算、事件或结局。
- 语言风格与人物档案一致。
- 能记住玩家承诺、冲突、历史谈判和已公开信息。

### 7.6 NPC 指标评估

NPC 指标变化必须由目标 NPC 的 LLM 依据自身角色设定、规则、记忆、上下文和玩家说服文本输出结构化结果。系统不得只用固定表格替代 NPC 的态度判断。

这是本游戏的核心机制：玩家通过文字与 NPC 互动，文字被传入该 NPC 的大模型，由该 NPC 根据“自己是谁、知道什么、怕什么、想要什么、当前是否信任玩家、玩家刚才说了什么”来决定指标变化。

LLM 输入至少包含：

- NPC 固定档案。
- NPC 当前运行时指标。
- NPC 记忆和已知信息。
- 玩家本次输入的完整说服文本。
- 行动解析器给出的辅助行动标签。
- 当前世界状态。
- 相关事件和承诺。
- NPC 的行为边界、红线、收益函数和语言风格。

LLM 输出必须是固定格式 JSON。第一阶段建议包含：

```json
{
  "npc_id": "npc_yang_deqing",
  "attitude_delta": {
    "trust_to_player": -6,
    "attitude_score": 3,
    "anxiety_level": 8,
    "reference_point": 0
  },
  "state_flags": {
    "core_demand_satisfied": false,
    "signed_intent": false,
    "will_share_with": ["npc_li_ergu"]
  },
  "reasoning_summary": "玩家提到提高补偿，但没有回应祖坟问题。角色短期愿意继续谈，信任下降，焦虑上升。",
  "dialogue_intent": "继续试探玩家，不直接拒绝",
  "risk_notes": ["祖坟问题未处理，后续可能串联同组老人"]
}
```

系统校验职责：

- 检查 JSON 格式。
- 检查指标变化是否超过允许范围。
- 检查是否触发非法承诺或越权行为。
- 检查 NPC 是否引用了自己不知道的信息。
- 检查 `signed_intent` 是否满足签约必要条件。
- 对超出范围的数值进行裁剪或要求 LLM 重试。

系统提交职责：

- 合法的指标变化写入 `NPCState`。
- LLM 的 `reasoning_summary` 写入审计日志。
- 风险提示进入事件或夜间推演候选。
- 签约状态不能只凭 `signed_intent` 直接改变，仍需满足预算、程序和行动条件。

禁止实现方式：

- 禁止用“玩家选择 A，则 NPC 信任 +10”作为主要结算方式。
- 禁止只根据关键词匹配决定 NPC 指标变化。
- 禁止让 ActionParserService 或 ActionService 直接决定 NPC 是否被说服。
- 禁止把快捷行动设计成替代文字说服的主玩法。

### 7.7 LLM 对抗性与难度

游戏难度与 NPC 对抗程度挂钩。系统需要支持难度参数：

| 难度 | NPC 行为 |
|---|---|
| 教学 | NPC 给出较多线索，较少误导 |
| 标准 | NPC 保持诉求和防御，少量试探 |
| 困难 | NPC 更容易串联、观望、反悔、要价 |
| 研究 | 行为参数由实验条件控制，不以通关体验为优先 |

难度只改变概率、阈值、信息失真和对抗程度，不改变基本事实。

### 7.8 夜间推演

夜间推演必须支持：

- NPC 之间的信息传播。
- 补偿金额传闻扩散。
- 信息失真。
- 意见领袖级联影响。
- 高焦虑 NPC 主动行动。
- 干部私下协调或阻挠。
- 媒体线索获取。
- 隐藏证据转移或暴露。
- 次日摘要生成。

夜间完整日志默认对玩家不可见，只在复盘页展示。

### 7.9 事件系统

事件分为四类：

- 固定事件：到达特定行动日触发。
- 条件事件：状态满足阈值触发。
- 随机事件：从事件池抽取。
- 玩家行动触发事件：由特定行动链触发。

每个事件必须包含：

- `event_id`
- 名称
- 触发条件
- 是否可重复
- 玩家可见文本
- 可选项
- 状态影响
- NPC 状态影响
- 后续影响
- 复盘解释

### 7.10 存档与读档

存档功能是第一阶段必做能力。第一阶段采用“自动存档 + 继续最近一局 + MySQL 保存当前状态 + JSON 快照辅助回放”的方案。

系统必须在以下节点自动保存：

- 开局。
- 每次玩家行动后。
- 每次 NPC 回复后。
- 日终结算后。
- 夜间推演后。
- 重大事件触发后。
- 结局判定后。

玩家登录后，首页必须提供：

- 继续游戏：读取该账号最近一局未结束游戏。
- 新开一局：创建新的 game session。

第一阶段存档不要求支持：

- 手动多存档槽。
- 玩家选择历史节点回滚。
- 任意行动日前重新开始。
- 删除存档的前端入口。
- 展示完整历史局列表。

读档后必须恢复：

- 当前行动日。
- 行动点。
- 所有指标。
- 所有 NPC 状态。
- 玩家承诺。
- 已触发事件。
- 可见和不可见日志。
- 对话历史。
- 剧本版本和规则版本。

存档归属规则：

- 每个存档必须绑定 `account_id`。
- 普通玩家只能读取自己的存档。
- 管理员和研究者读取他人存档需要后续权限系统支持。第一阶段可以只开放管理员本地调试接口。
- 删除存档第一阶段不做前端入口，避免误删研究数据。
- MySQL 是权威状态源。JSON 快照是辅助证据源，用于调试、复盘和研究回放。

### 7.11 前端

第一阶段游戏前端采用三栏布局：

- 左侧：行动日、行动点、预算、核心指标、干部信任度、警报。
- 中间：对话流、玩家输入框、快捷行动、日终结算卡。
- 右侧：手绘地图、NPC 档案抽屉、事件日志、证据库。

前端不应把玩法说明写成大段教程。开局只提供 5 步上手教程：

1. 查看今日状态。
2. 选择行动对象。
3. 使用行动点交互。
4. 日终查看指标变化。
5. 90 日后按结果进入结局和复盘。

登录页面要求：

- 游戏页面前必须进入登录页。
- 登录页只包含用户名、密码和登录按钮。
- 第一阶段不显示注册入口，账号由管理员或种子脚本预置。
- 登录成功后进入游戏首页。
- 登录失败给出通用错误提示，不暴露用户名是否存在。

### 7.12 复盘

复盘页必须包含：

- 最终评分。
- 结局文本。
- 关键指标曲线。
- 3-5 个关键决策回顾。
- 玩家不知道的夜间互动。
- 关键 NPC 真实诉求揭示。
- 暗线处理结果。
- 可导出的完整日志。

## 8. 指标需求

第一阶段核心指标：

| 指标 | 初始值 | 用途 |
|---|---:|---|
| `signed_households` | 0 | 搬迁进度 |
| `budget_remaining` | 8000 | 预算约束 |
| `social_stability_index` | 70 | 群体事件风险 |
| `political_credit` | 70 | 上级评价和玩家权力空间 |
| `cadre_execution_index` | 60 | 干部执行质量 |
| `public_trust` | 50 | 群众信任 |
| `env_clue` | 0 | 环评暗线进度 |
| `media_pressure` | 30 | 舆情压力 |
| `days_left` | 90 | 时间约束 |

所有指标必须有上下限、阈值和触发后果。数值变化必须写入日志。

## 9. 数据需求

系统必须保存以下数据：

- `Account`：账号、密码哈希、基础角色、创建时间。
- `Session`：一局游戏的元数据。
- `GameSnapshot`：每个关键节点的完整状态。
- `ActionLog`：玩家行动。
- `DialogueLog`：玩家与 NPC 对话。
- `NightLog`：夜间 NPC 互动。
- `EventLog`：事件触发和玩家选择。
- `PromiseLog`：玩家承诺和兑现状态。
- `EndingLog`：结局和评分。
- `ExperimentMetadata`：实验条件、剧本版本、模型版本。

研究导出至少支持 JSON 和 CSV。

第一阶段主数据库采用 MySQL。JSON 文件只作为调试、快照和复盘辅助产物，不作为账号、存档和研究日志的主存储。

## 10. 非功能需求

### 10.1 稳定性

- 单局游戏中断后可恢复。
- LLM 调用失败不应导致状态损坏。
- 夜间推演失败时可降级为规则摘要。
- 所有状态变更必须可回放。

### 10.2 成本

- 第一阶段单局 LLM 调用成本应可配置上限。
- 夜间推演优先使用规则引擎。
- 只有高价值 NPC 对话和摘要生成调用 LLM。

### 10.3 安全

- API Key 不进入前端。
- 密码必须使用安全哈希算法保存。
- 登录接口必须使用服务端校验。
- 普通用户不能读取其他账号的存档。
- 玩家输入要做长度限制。
- LLM 输出要做规则校验。
- LLM 输出的 NPC 指标变化必须保留原始 JSON 和校验结果，便于复盘和研究。
- 导出研究数据时默认匿名化。

### 10.4 可维护性

- 剧本、NPC、规则、Prompt、模型配置分离。
- 规则模块必须有单元测试。
- 关键阈值应配置化。
- 文本内容尽量放在剧本包中，不写死在业务代码中。

## 12. 验收标准

第一阶段进入内测前必须满足：

- 玩家能从 D1 玩到结局。
- 存档中断后恢复状态一致。
- 系统能拒绝非法行动。
- NPC LLM 能输出结构化指标变化，系统能校验并提交合法变化。
- 夜间推演能产生隐藏日志和可见摘要。
- 至少 8 种结局能通过测试脚本覆盖。
- 所有固定事件可触发。
- 单元测试全部通过。
- 复盘页能展示关键日志。

## 13. 实现闭环补充

### 13.1 剧本、规则与 NPC LLM 的职责边界

剧本不是一段只用于开场展示的文本，也不是替 LLM 逐句写好回答的对话树。它是游戏的**内容与事实权威**，用于定义世界中已经发生或允许发生的事；LLM 是受剧本约束的角色执行者；规则系统是唯一的状态提交者。

| 层级 | 必须负责 | 不得负责 |
|---|---|---|
| 剧本包 | 世界事实、时间节点、人物档案、地点、线索、事件、结局条件、可见/隐藏信息、对话开放条件 | 根据玩家一句话直接写入运行时状态 |
| NPC LLM | 以该 NPC 身份理解玩家原话，判断可信度、情绪、态度、愿不愿意继续谈、愿分享或传播什么信息，并输出受限 JSON 和角色台词 | 发明剧本外事实、越过知识边界、直接签约、扣预算或改结局 |
| 规则系统 | 合规、资源扣除、事件触发、数值边界、签约程序、状态事务、存档、结局判定 | 用固定选项表替代 NPC 对说服效果的判断 |

旧版剧本提示词中“分支和指标变化写死”的要求，应在制作时拆成两类：

- 必须写死：事实真相、线索位置、事件触发条件、NPC 知识边界、红线、可兑现政策范围、签约和结局的必要条件。
- 允许在边界内动态生成：NPC 对措辞、承诺可信度、过往关系和当前局势的态度变化，及其自然语言回应。

因此，剧本必须提供“可解释的结果区间和触发条件”，而不是把每句玩家文本映射为唯一的固定数值。这样既保留 LLM 角色博弈，又能保证剧情不会脱离设计稿。

### 13.2 玩家如何获得与 NPC LLM 互动的机会

玩家不能在任意时刻对任意角色无限制地发消息。每次可互动机会由剧本包中的 `interaction_opportunity` 定义，并由前端以地图、任务、事件、档案或已解锁线索呈现。它至少包含：

- `opportunity_id`、关联 `npc_id` 或 `location_id`。
- 开放条件：日期、前置事件、已知线索、关系阈值、是否在场、冷却时间。
- 入口类型：地图走访、来访事件、会议、电话、档案追问、媒体采访或玩家主动约谈。
- 行动点、预算或时间成本，以及是否允许自由文字输入。
- 该 NPC 在本机会中可谈范围、不可谈范围、可解锁信息和关闭条件。
- 失败、拒绝、延后或转化为新机会的后果。

标准流程为：剧本或事件开放机会 -> 玩家在地图/任务/档案中选择对象 -> 系统显示本次会面背景、成本与已知议题 -> 玩家输入说服、追问或承诺 -> 目标 NPC LLM 在自身人设和当前记忆内回应并评估态度 -> 系统校验、保存并可能开放下一条机会。玩家也可以通过与一个 NPC 的对话、取得证据或处理事件，解锁原本不可接触的 NPC、地点和话题。

### 13.3 单局节奏与 90 日设定

90 日是叙事和状态时间轴，不等于玩家必须完成 90 次完整操作。为满足单局约 45 至 55 分钟的目标，剧本包必须定义“关键行动日”和“可快进日”：

- 关键行动日必须提供至少一个重要互动、事件或决策机会；第一版建议控制在 18 至 24 个。
- 非关键日可由玩家选择日程推进，系统只结算低风险规则和简短摘要，不强制逐日对话。
- 每个关键行动日最多出现 1 个主事件和 1 个可选支线，避免信息与 LLM 调用失控。
- 90 日结束、强制失败、主线完成或剧本规定的提前结局均可结束游戏。

### 13.4 第一版内容生产准入

任何可进入内测的剧本包必须同时具备：

- `npc_profiles.json`：最终 `npc_id`、人物目标、知识边界、记忆种子、语言风格、红线、关系和可见性。
- `interaction_opportunities.json`：所有对话/行动入口及开放、关闭和解锁规则。
- `story_beats.json`：开局、关键日、固定事件、暗线节点、结局前置条件和可快进日。
- `facts_and_clues.json`：事实、证据、来源、可信度、发现方式、可被哪些 NPC 知道的范围。
- 规则、事件、结局、Prompt 与美术资源清单，并全部带 schema 版本。

缺少上述任一项的剧本只能作为文学母稿或概念稿，不能直接进入运行时。
