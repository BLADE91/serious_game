# 《浊流之下·清江搬迁记》角色 LLM Token 上限预算

## 1. 结论

在采用本文硬限制的前提下，角色 LLM 的开发期总预算建议设置为：

```text
角色专项开发与测试：243,000,000 tokens
共享 Prompt、引擎集成和整局回归：20,000,000 tokens
剧本修订、失败重试与临时实验储备：12,000,000 tokens
项目开发期 max：275,000,000 tokens
最低立项预算线：250,000,000 tokens
```

其中单个承重角色的最高开发预算为 `15,000,000 tokens`。该数字是输入 token 与输出 token 之和，不含图片生成，不等于模型费用。

如果不增加调用次数和对话轮次限制，当前剧本写明“对话轮次不限”，理论 token 上限是无限，无法给出有限 `max`。本文把 `250M` 视为正式产品开发的最低预算线，把 `275M` 作为建议硬上限；成立前提是开发和运行时都执行第 2 节硬限制。

本次估算不再采用“单模型、少量样例即可定稿”的精简口径，而是假设每个承重角色都要经历多模型候选对照、多个 Prompt 版本、正常与对抗输入、六章跨章记忆、不同人物关系状态、失败修复以及整局路线回归。这样更接近角色驱动型严肃游戏正式开发的实际工作量。

## 2. 估算口径与硬限制

### 2.1 单次角色调用上限

每次原子 NPC 回合使用一次受控模型调用，同时返回角色回复、态度/焦虑幅度档、吐露候选、传播候选和审计字段。

| 内容 | 单次上限 |
| --- | ---: |
| 系统规则、权限边界、JSON Schema | 2,500 tokens |
| 人物档案、语言风格、知识边界 | 2,500 tokens |
| 当前章节、世界状态、可见事实 | 2,000 tokens |
| 结构化记忆、承诺、最近对话摘要 | 4,000 tokens |
| 玩家本轮输入及动作上下文 | 1,000 tokens |
| 预留与序列化开销 | 2,000 tokens |
| 单次最大输入 | **14,000 tokens** |
| 角色回复与结构化 JSON 最大输出 | **2,000 tokens** |
| 单次计费 token 硬上限 | **16,000 tokens** |

要求：

- 超出 14K 的历史不能继续原样拼接，必须摘要、裁剪或按相关性检索。
- 每次调用最多一次 JSON 修复重试；修复重试计入角色的开发调用次数和全局 token 预算。
- NPC 运行时不使用长思维链输出；若模型产生 reasoning tokens，也必须计入输出预算。
- 固定剧情已有硬结算时，模型只生成角色化反馈，不重复调用“评估模型 + 对话模型”两次。
- 开发测试应从 API 的真实 usage 字段累计输入和输出，不能按字符串长度自行估算结算量。

### 2.2 开发档级

| 开发档 | 适用角色 | 最大计费调用次数 | 单角色开发 max |
| --- | --- | ---: | ---: |
| A+ 承重角色 | 多章主线、关键证据、复杂对抗或结局轴核心 | 约 937 次 | 15,000,000 |
| A 深度角色 | 第一档长期自由对话、户数攻坚或重要民心节点 | 约 625 次 | 10,000,000 |
| B 有限角色 | 第二档、教学主持、职能部门或较少自由互动 | 约 312 次 | 5,000,000 |
| B- 单章承重 | 单章关键出场，需要若干对抗与一致性测试 | 约 187 次 | 3,000,000 |
| C 薄角色 | 配角、事实函数型角色、从众型薄角色 | 约 125 次 | 2,000,000 |
| D 氛围角色 | 第三档、公开信息和氛围回复 | 约 62 次 | 1,000,000 |

每个档级的调用次数已经包含：人物 Prompt 初建、多模型与多版本对照、正常说服测试、无效策略测试、越权诱导测试、知识边界测试、跨章记忆测试、JSON 校验失败重试、夜间传播测试和整局路线回归。不是每次都必须把 16K 用满，但预算按全部打满计算。

## 4. 共享开发预算

以下 token 不适合拆到单一角色名下：

| 项目 | max tokens | 用途 |
| --- | ---: | --- |
| 全局 System Prompt 与 JSON Schema 调试 | 4,000,000 | 权限边界、输出格式、注入防护、失败降级 |
| 关系网络与夜间传播回归 | 4,000,000 | 多角色传播、知识来源、重复结算与不可传播信息 |
| 六章整局自动回归 | 8,000,000 | 多种路线的跨章记忆、机会解锁、强制节点与结局一致性 |
| 对抗、安全和越权测试 | 2,000,000 | Prompt 注入、诱导造旗标、索要隐藏状态、超知识回答 |
| 摘要、压缩和成本控制调试 | 2,000,000 | 长对话裁剪、结构化记忆、上下文超限和降级策略 |
| **共享合计** | **20,000,000** |  |

角色专项与共享预算合计为 `263,000,000 tokens`。另设 `12,000,000 tokens` 用于失败重试、Prompt 返工、模型切换和剧本变更，建议开发期硬上限为 `275,000,000 tokens`。其中 `250,000,000 tokens` 只作为最低立项预算线，不作为可随意突破的实际消耗目标。

## 5. 单局运行时 Max 建议

开发预算和正式玩家运行预算必须分开。建议正式单局设置以下硬上限：

| 调用类型 | 单局数量上限 | 单次 token 上限 | 单局 max |
| --- | ---: | ---: | ---: |
| 玩家发起的原子 NPC 回合 | 60 次 | 16,000 | 960,000 |
| JSON 修复重试 | 12 次 | 16,000 | 192,000 |
| 夜间关键 NPC 评估 | 24 次 | 12,000 | 288,000 |
| 章节摘要、记忆压缩 | 12 次 | 8,000 | 96,000 |
| 复盘与结局叙事校验 | 4 次 | 12,000 | 48,000 |
| **单局运行理论 max** |  |  | **1,584,000** |

考虑序列化误差和少量服务重试，建议正式配置：

```text
每局软警戒线：1,300,000 tokens
每局硬上限：1,600,000 tokens
计费与监控告警上限：2,000,000 tokens
```

到达软警戒线后，停止开放新的非关键自由对话，只保留当前剧情必需机会；到达硬上限后使用剧本明确登记的规则化回复与摘要，不得继续产生人物数值变化。不能在玩家不知情的情况下把同一角色换成行为不同的低成本模型。

## 6. 必须先修正的设计问题

1. `最终剧本.md` 明确写了自由对话“轮次不限”，而 `technical_design.md` 又要求每局设置调用次数和 token 预算。两者必须统一，否则实际 max 为无限。
2. 贺兴邦出现在 23 名主要人物和第六章关键剧情中，但没有出现在三档交互表。本文暂按第二档有限交互估算；实现前必须补入正式 Schema。
3. 李致远是玩家，不得建立一个替玩家自动表态的角色 Agent。表中的 500K 只用于身份、教程和系统旁白测试。
4. 固定决策点和突发事件已有剧本硬结算时，NPC 角色化回复应与受限评估合并成一次调用；拆成两个模型调用会近似翻倍消耗。
5. 必须记录每次调用的 `npc_id / chapter_id / opportunity_id / input_tokens / output_tokens / retry_count / cache_hit / model_id`，才能按角色核算预算并在达到上限前降级。
