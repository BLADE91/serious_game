# 剧本草稿存储说明

`outputs/script_drafts/` 保存章节式生成的创作源、中间结果、最终结果和人工修订版本。Markdown 是创作事实源，JSON 是从 Markdown 抽取出的运行结构。

## 目录结构

```text
outputs/script_drafts/
├── .version_counter
└── v01/
    ├── 00_generation_request.json
    ├── .source_baseline/
    │   ├── 01_game_settings.md
    │   ├── 02_chapter_outline.md
    │   └── 03_chNN.md
    ├── .artifact_inputs.json
    ├── 01_game_settings.md
    ├── 02_chapter_outline.md
    ├── 03_ch01.md
    ├── 03_ch02.md
    ├── 04_merged.md
    ├── 05_continuity_review.json
    ├── 06a_global.json
    ├── 06b_ch01.json
    ├── 06b_ch02.json
    ├── 06_script_structure.json
    ├── 07_validation_report.json
    ├── final_YYYYMMDD_HHMMSS.md
    ├── script_generate_YYYYMMDD_HHMMSS.json
    └── revisions/
        ├── r01/
        │   ├── 01_game_settings.md
        │   ├── 02_chapter_outline.md
        │   ├── 03_chNN.md
        │   ├── .source_baseline/

        │   ├── revision_job.json

        │   ├── final_YYYYMMDD_HHMMSS.md
        │   └── script_revise_YYYYMMDD_HHMMSS.json
        └── r02/
            └── ...
```

章节数量决定 `03_chNN.md` 和 `06b_chNN.json` 的实际数量；每章决策点数量由生成请求指定，并由 Call 6 对抽取结果进行数量校验。没有进行修订时不会创建 `revisions/`。

## 文件职责

| 文件 | 产生阶段 | 说明 |
|---|---|---|
| `00_generation_request.json` | 创建版本时 | 保存原始生成参数，供 Web 续跑时复用 |
| `.source_baseline/` | 源 Markdown 稳定后 | 保存外部编辑前的源文件快照，用于“审查并重建”识别实际改动 |
| `.artifact_inputs.json` | 原始生成的派生产物写入时 | 保存各 JSON 产物的输入指纹，避免源文件变化后误用旧缓存；修订版的指纹写在 `revision_job.json` |
| `01_game_settings.md` | Call 1，PA Backend | 全局变量、玩家角色、NPC、结局和创作约束 |
| `02_chapter_outline.md` | Call 2，PA Backend | 章节计划、Flag 计划和结局可达性 |
| `03_chNN.md` | Call 3，PA Backend | 单章完整 Markdown，是局部修订的主要目标 |
| `04_merged.md` | 程序合并 | 连续性修复后的 01、02、03 完整合并稿 |
| `05_continuity_review.json` | Call 4，Qwen Flash + 程序 | 事实连续性问题、已应用补丁、拒绝补丁和复审结果 |
| `06a_global.json` | Call 5a，Qwen Flash | 全局结构、NPC 和结局抽取结果 |
| `06b_chNN.json` | Call 5b，Qwen Flash | 对应章节的剧情树抽取结果 |
| `06_script_structure.json` | 程序合并 | 06a 与全部 06b 的合并结果 |
| `07_validation_report.json` | Call 6，程序 | 必要结构和 Markdown 到 JSON 的 ID 提取完整性 |
| `08_revision_impact.json` | 修订管线 | 全局设定或大纲变化的影响级别、受影响章节和原因 |
| `final_*.md` | 最终保存 | 本版本的完整 Markdown |
| `script_generate_*.json` | 最终保存 | 原始生成版的完整结果 |
| `script_revise_*.json` | 修订完成 | 修订版的完整结果 |
| `revision_manifest.json` | 修订管线 | 修订来源、目标、方式、状态和校验摘要 |
| `revision_plan.json` | 批量修订编排 | 固定源文件、整体影响、执行顺序和最大并发数 |
| `revision_job.json` | 批量修订续跑 | 每个同步、审查、抽取和校验任务的状态、次数、输入指纹与输出哈希 |

当前没有 `05_revision_notes.md` 和独立的 `.*.hash` 文件；输入指纹集中存放在 `.artifact_inputs.json` 或 `revision_job.json`。

## 断点续跑规则

生成器同时检查文件状态和输入指纹：

- 文件存在且输入指纹一致：读取并跳过对应 Call。
- 文件存在但输入指纹变化：重跑对应 Call 并更新指纹。
- 文件缺失：执行对应 Call 并写回。
- `04_merged.md`：每次运行都由连续性修复后的 01、02、03 重新合并。旧版本的 `04_merged_before_review.md` 保留兼容，不作为新版本标准名称。
- `03_chNN.md`：缺少某一章时，Call 3 会复用已有章节并补生成缺失章节。
- `06a_global.json`：依赖合并后的 Markdown；`06b_chNN.json`：只依赖对应章节 Markdown。
- `06_script_structure.json`：依赖 06a 和全部 06b；任一分片变化都会重新合并。
- `07_validation_report.json`：依赖结构 JSON、合并 Markdown、连续性报告和预期数量。

Web 的“一键生成”始终创建新版本；“续跑”按钮会列出所有缺少 `script_generate_*.json` 的 `vNN` 供用户选择。续跑沿用 `00_generation_request.json`；旧版本没有该文件时，会从已有 `03_chNN.md` 推断章节数，并使用当前表单补足其他参数。

手动替换 Markdown 后，推荐使用 Web 的“审查并重建”：它从当前源文件创建新 `rNN`，不会复用旧 `06a/06b`，也不要求人工删除派生产物。程序优先对照 `.source_baseline/` 判断改动范围；历史版本没有基线时保守地同步全部章节。

## 修订版本

Web 和 CLI 的正式修订不会覆盖 `vNN/` 原版，而是在同代目录下创建平级的 `revisions/rNN/`。从 `r01` 再修订时会创建 `r02`，不会嵌套为 `r01/revisions/r02`。

Web 批量修订只复制 Markdown 源。程序合并分析所有文件变化，使用最多 3 个 Qwen Flash 任务并发同步受影响章节，再执行连续性审查和唯一文本补丁；Markdown 稳定后，全量重建 06a、全部 06b、合并结构、校验、final 和结果 JSON。AI 候选会同时读取本批次其他未提交草稿，JSON 不由修订 Agent 直接改写。

每个阶段写入 `revision_job.json`。续跑会重新比较父版本和当前 `rNN`，把失败后新增的全局设定或大纲改动合并进影响范围；只复用输入指纹一致、输出文件存在且输出哈希一致的已完成任务。源 Markdown 被再次人工修改时，对应同步、审查、抽取和校验任务会自动失效。所有正式产物都写入新 `rNN`，原版本保持不变。

Web 的批量提交、审查重建和续跑共用 SSE 任务接口，前端展示当前阶段和完成数量，并可请求取消。取消不会删除已完成文件，之后可按上述规则安全续跑。

`revision_manifest.json` 的 `status` 为 `building`、`review_required`、`complete` 或 `failed`。未同步的受影响章节、程序校验问题、连续性建议以及无法自动处理的章节数量/顺序变化都会得到 `review_required`。主要字段包括：

```json
{
  "revision": "r01",
  "parent": "v01",
  "mode": "manual",
  "target": "ch02",
  "feedback": "",
  "revision_engine": "human",
  "sync_engine": "qwen_flash",
  "changed_files": ["01_game_settings.md", "03_ch02.md"],
  "resolved_chapters": ["ch02"],
  "unresolved_chapters": ["ch03"],
  "status": "review_required",
  "validation": {"valid": true}
}
```

## 版本编号

`.version_counter` 是快速计数状态，不是版本目录的唯一事实源。分配新生成版时，程序取计数器中的 `gen` 与磁盘已有最大 `vNN` 的较大值，再加 1；即使计数器落后，也不会复用已有目录。

- 全新生成：创建新的 `vNN/`。
- 指定已有 `--out-dir .../vNN`：原地断点续跑，不增加版本号。
- 正式修订：在对应 `vNN/revisions/` 下按现有最大编号创建 `rNN`。

## 校验报告

`07_validation_report.json` 当前使用 `validation_version: 2`，包括：

- `structure_validation`：章节、节点、选项、引用、NPC、结局等必要结构是否合法。
- `extraction_validation`：Markdown 中声明的 chapter、choice、npc、ending ID 是否完整进入 JSON。
- `continuity_review`：Call 4 的事实连续性问题、自动修复和最终复审状态。

`valid` 只表示自动结构与提取校验没有 error，不代表策略张力、教学质量、人物行为或叙事质量已经通过人工评审。

## 最终 JSON

最终结果顶层包含：

```json
{
  "script": {
    "chapter_npcs": [],
    "chapters": [],
    "chapter_endings": [],
    "validation_report": {}
  },
  "full_md": "# 完整剧本...",
  "generation_mode": "chapter",
  "generation_notes": [],
  "revision_round": 0
}
```

前端的版本列表和“最近结果”会同时扫描 `vNN/*.json` 与 `vNN/revisions/rNN/*.json`，并排除 `01` 到 `07` 的中间 JSON 和 `revision_manifest.json`。
